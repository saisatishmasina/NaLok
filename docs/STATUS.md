## F07.1 reliability pass (feat/Frontend, 2026-10-26) — review fixes
- Stale edits can no longer overwrite newer work: `ProjectSection` gained `@Version` (Project and StudySession already had it); DTOs expose `version`, PUT edit requests carry the snapshot's version (`UpdateProjectRequest`/`UpdateSectionRequest`, `@NotNull`), and services (`updateProject`/`updateSection`) compare it before writing — mismatch throws `OptimisticLockingFailureException`, mapped by the WIDENED handler (parent class covers both the explicit service check and ORM-detected staleness) as 409 "Concurrent update".
- Concurrent section creation cannot duplicate positions anymore: `appendSection` now takes the project row with a PESSIMISTIC write lock (`ProjectRepository.findByIdForWrite`) and reads sections through a locking query (`ProjectSectionRepository.findByProjectIdForWrite`) — the row lock serializes racing appends per project and the locking read sees the latest committed rows, so max(position)+1 is safe under REPEATABLE READ; both racing requests get distinct positions.
- Personal `nalok` DB keeps rows untouched — note the additive schema effects of ddl-auto=update on the next dev-server run: `project_sections.version` column.
- Refreshes no longer destroy state (frontend `useResource`): a refresh of the SAME resource (manual refetch or poll-triggered restart, detected via a deps comparison) KEEPS the last good data visible while reloading — open edit forms don't unmount and a failed refresh shows the retained data under a note instead of an error-only card; only a genuinely NEW resource (deps change) resets to loading. Requests are additionally coordinated ACROSS effect restarts: a hook-level `busyCount` gates polls, and a `refetch()` clicked while a load is in flight is DEFERRED (runs once when the in-flight load settles) instead of starting a second identical request; deferred intents are dropped if navigation changed the resource generation meanwhile.
- The edit forms now send the snapshot version and re-sync from the server after a failed save (the 409 message tells the user to reload and retry).
